# 玩家推荐方案服务

供 RTX-FG-Manager 4.3.6 及更新版本使用的独立服务：Node.js 24、SQLite、SMTP。浏览不需要登录，分享和点赞使用邮箱验证码。客户端只接收方案标识与已知 DLL 名称，不接收任意下载地址或执行命令。

4.3.7 使用 `X-RTXFG-Feedback: 5` 读取分享日期；旧协议不增加字段。列表按有用数量、更新时间、ID 排序后分页。数据库 schema 5 保留新分享的首次时间；旧记录只在未编辑时回填首次时间，无法确认的显示更新时间。升级前执行 `node src/backup.mjs` 并备份代码；回退旧服务需同时恢复对应数据库备份。

## 宝塔部署

1. 将本目录放到服务器独立目录，例如 `/www/rtxfg-recommendations`。不要放进现有网站的公开目录。
2. 运行 `node src/init.mjs 发件邮箱 管理员邮箱`，生成权限为 `600` 的 `.env` 和随机 `AUTH_SECRET`，然后填写 SMTP 授权码。初始化不会覆盖已有配置。也可手动复制 `config.example`，使用 `openssl rand -hex 32` 生成密钥。这些内容只留在服务器上。
3. 在该目录执行 `docker compose up -d --build`，用 `docker compose ps` 确认健康状态。
4. 将 `recommend.lgxng.cn` 解析到服务器，在宝塔添加独立站点，配置 HTTPS 和 `nginx-location.conf` 中的反向代理。不要开放 17836 或 8080 公网端口。
5. 访问 `/v1/health`，应返回 `ok: true`。在客户端通过真实邮箱完成一次登录，再由用户主动分享一条真实可用的方案。测试不会预填伪造玩家或点赞。

验证码 10 分钟有效、最多尝试 5 次；邮箱及 IP 均限流，默认每天最多发送 100 封。改用阿里云邮件推送等 SMTP 服务时只需修改服务器配置并重建容器，无需重新发布客户端。QQ 邮箱建议仅用于初期试用，并留意服务商的发送限制。

## 审核与数据

- 访问 `/admin` 或网站首页，使用 `.env` 指定的管理员邮箱获取验证码。支持全部方案、搜索、公开/隐藏/举报/疑似重复筛选，以及隐藏、恢复、删除方案和限制作者；每次管理操作留记录。删除前显示具体方案并确认，移除正文和评价；隐藏可以恢复。疑似重复只供人工比较，不会自动删除。管理页面不会把令牌保存到浏览器持久存储。
- 每个邮箱身份、每款游戏最多 5 个分享。作者可编辑或删除自己的方案；编辑更新同一条分享，不占新名额。“有用 / 无用”互斥、可切换和撤销，不能评价自己的分享。更新内容沿用原有评价；修订号用于拦截过时的编辑、删除和评价请求。原点赞保留为有用；旧测试客户端仍可浏览和点赞。邮箱验证不能证明每个账户对应不同自然人。
- 举报需选择原因，同一已验证邮箱计一次，可在“我的举报”中撤销。三个不同且未被限制的邮箱举报后暂时隐藏，不自动删除；撤销不会自动恢复已隐藏方案。管理员恢复公开时结案当前举报，同一举报人不能对已审核的同一版本反复提交；更新内容不会自动解除隐藏。仅个人电脑上无效可使用“无用”评价。
- 数据库 schema 4 增加游戏别名与归类记录，不改已有账户、分享和评价。升级前创建一致性备份；回退到旧服务必须同时恢复对应备份，不能用旧代码直接打开新数据库。反馈扩展 4 支持跨平台关联和平台/版本说明；旧客户端继续使用原游戏范围与字段。
- 删除分享后立即从 API 隐藏并删除内容和反馈。API 不使用公开 CDN 缓存；客户端已有的离线缓存会在下次成功刷新后替换。
- 数据保存在 Docker 命名卷 `recommendation-data`。升级时保留该卷，**不要执行 `docker compose down -v`**。升级前先备份，定期备份需要包含 SQLite 一致性快照，不能只复制正在写入的主数据库文件。
- 执行 `docker compose exec -T recommendations node src/backup.mjs` 创建一致性备份，文件存放在卷内的 `/data/backups`。应另外复制到受保护的异机备份位置。
- 不记录邮箱验证码、登录令牌、SMTP 授权码或请求正文。数据库内包含登录邮箱，应限制服务器和备份访问。

## 游戏归类

- 客户端复用启动器身份和当前版本名称规则的可靠结果，无法确定时仅需选择一次。手动名称不作为自动跨游戏关联依据；泛用的 `Client-Win64-Shipping` 不能单独判断是哪款游戏。
- 后台展开“游戏归类”，搜索玩家补充的名称，设为“待归类”；再搜索正确的完整游戏名，设为“正确游戏”。预览关联范围，确认属于同一款游戏后提交。新版客户端下次刷新即共同显示这些推荐；分享 ID、作者、评价和隐藏状态均保留。关联后每人五份的限制按整组计算，已有超额条目不自动删除。
- 支持撤销最近一次关联；后续关联或名称表新增会使旧撤销失效，避免覆盖后来变化。平台与玩家填写的游戏版本显示在分享中，不保证其他平台或重制版同样兼容。
- 服务随包使用与客户端相同的公开名称表。更新名称表后，在仓库根目录运行 `node recommendations/src/build-games.mjs`，测试并重新部署服务。玩家名称可搜索、人工核实后归类，不会未经审核写成全局自动识别规则。既有人工归类不会被新表覆盖。
- 公开读取接口为 `/v1/games?q=名称` 和 `/v1/recipes?game=游戏标识`，新版客户端使用 `X-RTXFG-Feedback: 4`。可用于后续整理玩家实际测试的方案、入口与反馈；不上传本机目录、用户名、日志或原始配置文件。

## 验证码服务监控

- `/v1/health` 检查 API；`/v1/health/mail` 单独检查验证码服务，正常返回 200，异常返回 503，公开响应不包含邮箱、授权码或 SMTP 原始报错。访问监控地址只读取检查结果，不触发邮件或 SMTP 连接。
- 服务每 5 分钟检查 SMTP 的 DNS、TLS 与授权；结果超过 10 分钟未更新则视为异常。同时检查应用每日发送限额，跟踪实际发送失败。仅收件地址拒收不视为整个服务故障。SMTP 接受邮件不等于已进入收件箱，验证连接也不能验证最终投递。
- Uptime Kuma 添加 HTTP(s) 监控上述邮件地址，建议间隔 60 秒、重试 2 次、超时 15 秒、故障每 30 次检查提醒，并选择独立于验证码 SMTP 的飞书等通知通道。启用恢复通知及证书到期提醒。API 与邮件分开检查，避免首页正常而验证码不可用。
- 收到告警后：在宝塔检查容器状态；如 QQ 邮箱授权失效，由管理员重新生成授权码，私下修改 `/www/rtxfg-recommendations/.env` 的 `SMTP_PASSWORD`，执行 `docker compose up -d --force-recreate`，保留数据卷。连接检查恢复后监控自动转绿；若是发信被拒绝，需真实发送一次验证码成功才能清除发送故障。额度耗尽会在下一计数日恢复（UTC 日界），不要靠重启绕过限额。
- 授权码没有由本服务设置的固定到期时间，但撤销授权、账号状态、服务商限制和网络都可能造成失效；不能承诺永久有效。管理员登录也使用此 SMTP，因此故障期间通过宝塔修复，不能依赖管理网页重新登录。

### 本地测试

```sh
pnpm install --frozen-lockfile --ignore-scripts
node --test tests/*.test.mjs
```

测试使用内存数据库和邮件替身，不发送真实邮件。覆盖一次性验证码、错误次数和有效期、并发限额、游戏隔离、分享配额、重复请求、点赞撤销、修订、审核、隐私字段与 HTTP 边界。
